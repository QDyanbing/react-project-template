# 日期时间库选型

## Day.js 1

维护主体：Day.js 团队和社区。

定位：提供日期时间解析、校验、计算和格式化能力的轻量日期时间库，API 采用不可变对象并支持链式调用。

优点：

- 核心体积较小，时区、相对时间和高级格式化等能力可以通过插件按需扩展。
- 日期时间操作返回新实例，不会直接修改原对象。
- API 简洁，常用的解析、计算和格式化操作容易阅读。
- 支持 Locale，并提供 UTC、Timezone、Duration 等常用插件。
- Ant Design 的日期时间组件默认使用 Day.js，组件值、表单值和业务计算可以保持相同的数据类型。

局限：

- 部分常用能力不在核心包中，需要了解并启用对应插件。
- 插件会扩展全局 Day.js 能力，项目需要统一管理，避免不同模块各自初始化。
- 复杂时区、时间区间和日历计算能力不如专门面向这些场景的方案完整。

## date-fns 4

维护主体：date-fns 团队和社区。

定位：以独立函数处理原生 `Date` 的日期工具库，通过按需导入组合日期时间能力。

优点：

- 函数粒度清晰，可以只引入实际使用的能力。
- 直接使用原生 `Date`，不需要引入新的日期对象类型。
- 函数式 API 便于组合和单元测试。
- 内置 TypeScript 类型并支持按需加载 Locale，时区场景可以使用配套扩展。

局限：

- 复杂操作通常需要组合多个函数，代码连贯性不如链式 API。
- 函数数量较多，需要熟悉不同函数的输入、输出和命名。
- Ant Design 日期时间组件使用 Day.js 类型，选择 date-fns 后仍需保留 Day.js 或增加类型转换。

## Moment.js 2

维护主体：Moment 团队和社区。

定位：提供完整日期时间能力的传统日期库，具有成熟的链式 API 和庞大的存量生态。

优点：

- API 和资料成熟，常见日期时间问题都有大量实践可供参考。
- 解析、计算、格式化、Locale 和时区扩展能力完整。
- 适合继续维护已经依赖 Moment.js 的存量项目。

局限：

- 官方已经将其定义为处于维护模式的遗留项目，不再增加新功能。
- 日期对象可变，调用修改方法时容易影响原对象。
- 不适合 Tree Shaking，Locale 和时区数据会明显增加产物体积。
- 官方不建议在新项目中继续选择 Moment.js。

## Luxon 3

维护主体：Moment 团队和社区。

定位：基于浏览器 `Intl` 能力构建的日期时间库，提供 DateTime、Duration 和 Interval 等完整抽象。

优点：

- 时区、时间段和时间区间是一等能力，适合复杂日期时间业务。
- DateTime 对象不可变，API 含义明确并支持链式调用。
- 国际化和时区能力主要建立在原生 `Intl` 上，不需要额外维护时区和 Locale 数据文件。
- 对时间偏移、夏令时和区间运算提供了较完整的表达能力。

局限：

- API 和日期模型比常规管理后台所需能力更重。
- 需要在原生 `Date`、Luxon DateTime 与 Day.js 之间进行转换。
- 与 Ant Design 默认日期类型不同，会形成两套日期时间抽象。

## 选型结论

选择 Day.js 1。

当前项目使用 Ant Design，其日期时间组件默认接收和返回 Day.js 对象。选择 Day.js 可以让组件交互、表单数据和日期计算保持一致，避免同时维护两套日期对象和转换逻辑。

Day.js 已经覆盖管理后台常见的解析、校验、计算、格式化和国际化场景，核心保持轻量，额外能力可以通过插件补充。date-fns 的函数式设计和按需引入能力较好，但与 Ant Design 的日期类型不一致；Luxon 更适合复杂时区和时间区间业务，作为通用模板的默认方案成本偏高；Moment.js 已进入维护模式，不适合作为新项目的默认方案。

项目统一使用 Day.js 处理日期时间。遇到现有插件无法清晰表达的复杂时区或区间业务时，再根据实际需求补充专用能力，不预先引入第二套日期时间库。
